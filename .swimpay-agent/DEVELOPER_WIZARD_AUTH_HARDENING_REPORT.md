# Developer Wizard Auth Hardening Report

Generated: 2026-05-07

## Summary

Sprint 9G hardened the Developer Integration Wizard auth boundary without changing payment behavior.

The wizard now refuses local development merchant bearers in production, renders a disabled unavailable state when no approved server token exists, and backend developer integration routes reject `Bearer test_*` in production.

## Changes

### Web merchant bearer boundary

- Added `resolveMerchantServerBearerToken`.
- Production with no explicit approved token returns `null`.
- Production with `test_*` explicit token returns `null`.
- Test/dev can still use `test_<merchant_id>` fallback.
- Dev fallback can be disabled with `SWIMPAY_ALLOW_DEV_MERCHANT_SESSION=false`.

### Developer wizard unavailable state

- Credential, webhook URL, test webhook and retry buttons are disabled when backend lifecycle is unavailable.
- POST actions remain safe and render unavailable/action-not-recorded messages.
- One-time secrets only render from immediate successful backend action responses.

### Backend production guard

- `parseMerchantId` now supports `allowTestBearer`.
- `/v1/merchant/integration*` routes pass `allowTestBearer=false` in production.
- Production `Bearer test_*` no longer reaches integration repository mutations.

### Receiving-method request auth

- `ApiMerchantRouteAdminClient` now sends Authorization and Content-Type on create/update.
- Reads and writes use the same server-side merchant bearer.

## Tests added

- Production web resolver does not create local dev bearer.
- Production explicit `test_*` token keeps wizard unavailable.
- Production wizard POST key action does not reveal one-time secrets.
- Receiving-method writes include Authorization and Content-Type.
- Production API developer integration routes reject `Bearer test_*`.

## Safety posture

Preserved:
- no auto-confirmation;
- no official bank confirmation claim;
- no LLM/payment-decision changes;
- no real notification processing;
- no raw phone/card/notification text exposure;

## Remaining limitations

- Merchant web routes still need real authenticated merchant session and CSRF protection.
- API keys generated by the developer lifecycle are not yet used as production auth for all merchant API routes.
- Some older merchant pages remain process-global/demo surfaces and should be protected before public production exposure.
